# Project Structure Template

面向 AI 开发的新项目起点：用需求文档生成技术选型、工程骨架、协作规范、工具配置和项目知识。

本仓库当前处于**模板状态**。它提供通用大纲和生成流程；业务代码、技术栈、运行命令尚未生成。

## 快速开始

准备好需求文档，替换下面提示词中的项目名称、目标目录、需求文档和已有约束，然后交给具备文件与终端操作能力的 AI 执行。

本模板用于一次性初始化。完成后，新项目拥有自己的正式工程和说明文件；后续 AI 直接读取这些文件开展开发。

```text
请使用以下模板，为我初始化一个新项目：

模板仓库：
https://github.com/YYT-0901/Project-Structure-Template-4-AI-Era.git

项目名称：<项目名称>
目标目录：<本地目录>
需求文档：<文档路径或需求正文>
已有约束：<指定技术、部署环境等；没有则写“无”>

这是一次性的项目初始化任务。请直接完成初始化，交付一个可以开始正式开发的工程。

一、获取并理解模板

将模板获取到目标目录。
若目录已有内容，先检查并保留现有工作，不覆盖已有实现。

读取模板中的 AGENTS.md、初始化流程及相关文件，理解其组织约定。
模板仓库仅用于获取初始化材料，不向其推送新项目内容。

二、根据需求生成正式项目

1. 整理需求
   提取项目目标、范围、核心流程、关键约束和验收条件。
   保留需求来源，登记尚未明确的问题。

2. 确定技术栈
   尊重已有约束，其余技术选择根据需求自主确定。
   核实版本、兼容性与官方资料，记录选型理由。
   仅引入当前项目需要的组件。

3. 构建工程骨架
   按所选框架惯例建立源码目录和模块边界。
   配置依赖、环境示例、启动、检查、测试和构建入口。
   提供验证工程可运行所需的最小实现。
   业务需求用于指导工程设计，本次不展开完整业务功能开发。

4. 生成正式 AI 协作文件
   将 AGENTS.md、rules、skills 和 MCP 配置按实际项目填写。
   明确规则作用范围、技能触发条件和工具连接状态。
   不引入与当前项目无关的规则或工具。

5. 生成正式项目知识
   根据需求、技术决策和实际工程填写 .memories/，更新索引。
   明确区分已确定设计、已实现内容和待验证事项。
   关键描述附真实文件路径或需求依据。

三、结束初始化

将 README.md 改为本项目的正式说明，包含真实运行命令。

将正常工作入口切换为本项目自己的 AGENTS.md、rules、skills、
.memories/ 和相关需求文件。移出正常入口中的模板占位说明与初始化指令；
初始化记录仅作为历史依据保留。

后续开发应直接遵循这些正式文件，无需重新读取模板仓库或重复初始化流程。

执行适用的安装、启动、检查和构建验证。
未执行的检查不得标记通过；未解决的问题需说明影响。

关键业务歧义集中提出，其他初始化工作继续推进。
常规工程选择在上述约束内自主完成。

最终交付：
- 已确定的技术栈及理由。
- 项目目录与正式文档入口。
- 安装、启动、检查和构建方法。
- 实际验证结果。
- 尚待明确的事项。
```

初始化阶段、产出与验收细则见 [初始化流程](docs/bootstrap.md)，执行证据记录在 [初始化任务](.tasks/initialization.md)。

## 固定结构

```text
.
├── README.md                   项目入口，初始化后改写为产品说明
├── AGENTS.md                   AI 协作入口与规则路由
├── .agents/
│   ├── README.md               rules / skills / MCP 的职责与加载说明
│   ├── rules/                  可复用工程规范与项目专项规范
│   ├── skills/project-bootstrap/SKILL.md
│   └── mcp/                    连接清单、权限与配置示例
├── .memories/
│   ├── README.md               项目知识索引
│   └── 01-…08-….md             项目概览、架构、开发与业务知识
├── .tasks/                     当前任务、方案、进度与验证记录
└── docs/
    ├── bootstrap.md            初始化阶段、产出与验收
    ├── prompts/bootstrap.md    可直接交给 AI 的初始化指令
    ├── requirements/           原始需求与结构化摘要
    └── decisions/              技术选型与重要设计决策
```

语言、框架、源码目录、测试工具、数据库、部署方式按需求确定。固定的是协作与文档结构；代码组织遵循选定框架的惯例，并记录模块边界，避免每次由模型自由发明。

## 各类内容放在哪里

| 内容 | 维护位置 | 原则 |
| --- | --- | --- |
| 用户要什么、验收什么 | `docs/requirements/` | 保留来源，区分需求和建议 |
| 为什么选择这个方案 | `docs/decisions/` | 记录取舍、状态和适用条件 |
| AI 每次如何开始工作 | `AGENTS.md` | 简短入口，指向详细规范 |
| 必须遵守什么 | `.agents/rules/` | 标明作用范围与验证方式 |
| 某类任务如何完成 | `.agents/skills/` | 明确触发条件、输入和产出 |
| 可以连接什么工具 | `.agents/mcp/` | 声明连接不代表安装成功或获得操作授权 |
| 项目目前是什么样 | `.memories/` | 只把有依据的内容写为事实 |
| 这次做到哪里 | `.tasks/` | 记录当前进度和未完成事项 |

同一规则只维护一份正文；其他文件链接引用。工具专用配置从这些来源适配，并记录加载验证结果。

## 模板填写约定

- `[待补充]`：缺少输入，不得自行补成已确定事实。
- `[待实现]`：已有设计，代码或配置尚未落地。
- `[未验证]`：已经生成，但尚无运行证据。
- `不适用：原因`：确实不需要的能力，不为填满目录引入依赖。

初始化后仍可保留非阻塞待办，但必须列出影响；验收必需项未完成时不能宣布初始化完成。需求和方案支持的内容可以先记录为设计，必须标明状态。

## 完成标准

- 技术选型有需求依据、明确版本和取舍。
- 项目能从干净环境按文档安装、启动、检查与构建；不适用项有解释。
- 最小可运行路径与真实需求有关，且有可观察的结果。
- `AGENTS.md`、rules、skills、MCP 的入口与实际使用工具相符。
- `.memories/` 指向真实文件，区分已实现、设计和待验证内容。
- 初始化任务包含执行命令、结果、未完成事项和需求对应关系。

这些标准约束产出与验证，不能保证不同模型逐字生成相同代码。
