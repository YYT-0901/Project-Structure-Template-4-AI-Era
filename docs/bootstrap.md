# 从需求到可开发项目

## 输入与续接

必需输入：原始需求文档或可访问的需求内容、目标项目目录。已有技术约束和部署条件按原样保留；未提供的内容登记为问题。

先检查目标目录和 `.tasks/initialization.md`。已有项目只补齐缺失阶段，禁止重新脚手架覆盖实现。模板首次使用时，先读需求和现有规则，再填写记忆；不要把模板大纲当作项目事实。

## 1. 需求梳理

产出：`docs/requirements/project.md`。

提取目标用户、业务流程、范围、数据、权限、非功能约束和验收条件。保留原文，给需求分配稳定编号。明确哪些信息来自用户，哪些是建议、假设或问题。

verify：每个范围内功能都有来源和可观察的验收条件；影响后续决策的问题已解决或明确阻塞范围。

## 2. 技术选型

产出：`docs/decisions/0001-tech-stack.md`。

先满足用户指定技术；对开放项按需求比较合理候选，解释推荐方案及代价。仅在需要时引入后端、数据库、缓存、队列、容器和微服务。核实最终选用版本的官方资料、兼容性和维护状态，记录来源与核实日期。

选型尚未确定时可记录候选与建议，不安装会锁定方案的依赖。用户已授权自主选型时可在约束内作出决定并记录依据，无需重复索要同一授权。

verify：每个采用的组件都有用途、版本和依据；关键决定已在授权范围内确定；不需要的组件标明原因。

## 3. 工程骨架

产出：符合所选框架惯例的源码、依赖与锁定配置、配置示例、检查和构建入口。

先记录目录职责与依赖方向，再生成最小可运行实现。围绕一条真实需求建立可观察路径，避免填充无关业务。按项目类型提供必要的格式化、静态检查、测试、构建和持续集成配置；外部服务不可用时明确本地替代方式及其验证边界。

verify：从干净环境安装依赖，运行适用检查，启动并验证最小路径，完成构建。记录工作目录、命令、前置条件和结果。

## 4. AI 协作配置

产出：项目化的 `AGENTS.md`、适用 rules / skills、MCP 清单及所选客户端的必要适配。

保留通用规则，按真实目录加入语言、架构、接口、UI 等专项约束。只引入当前任务确实需要的技能和工具。MCP 未连接时写清状态，不用虚构服务填满配置。不复制其他项目的环境、标识或授权。

verify：用一个实际开发任务验证入口可读取、规则适用范围正确、相关 skill 能找到；需要的 MCP 通过最小只读调用验证连接。工具受限时登记未验证项与影响，不能声称配置已生效。

## 5. 项目知识

产出：`.memories/README.md` 及八个基础知识文件。

用需求整理业务，用已确定决策记录设计，用真实文件和运行结果记录实现。为关键描述附来源；尚未实现的架构必须标为设计，不写成当前能力。无相关功能的章节写明不适用理由。

verify：索引和路径有效；文档与源码、配置、命令一致；无依据的推测没有被写成事实。

## 6. 验收与交接

产出：改写后的产品 README、`.tasks/initialization.md` 中的验收证据和剩余事项。

按本流程逐项复核，移除已解决占位符。保留仍然有效的问题、限制和后续任务。任何验收必需项未通过，状态保持进行中或受阻；说明哪些部分可继续开发。

verify：需求 → 选型 → 文件/实现 → 验证证据可以追溯；README 提供从安装到运行的真实步骤；另一位开发者或 AI 能按入口继续工作。
